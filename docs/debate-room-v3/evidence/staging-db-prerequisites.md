## Release-blocking default-privilege finding

Hosted `postgres` default privileges in `public` grant full table privileges (`arwdDxtm`) to **anon, authenticated and service_role**, and EXECUTE to those roles for new functions. The original Debate migration revokes table privileges from PUBLIC/anon/authenticated, but omits service_role. Its subsequent `GRANT SELECT,INSERT,DELETE` on the audit table does **not** remove the inherited UPDATE/TRUNCATE/REFERENCES/TRIGGER/MAINTAIN privileges. RLS does not stop this because the service role bypasses it.

The local candidate correction now revokes all existing/default service-role table privileges alongside the browser roles before applying the exact explicit service-role grants. The hosted probe must still prove audit UPDATE denial and its intentional SELECT/INSERT/DELETE operations using the **actual hosted default-ACL shape**, including absence of TRUNCATE/REFERENCES/TRIGGER/MAINTAIN on the new Debate tables. Study admission already revokes service_role table grants explicitly and uses narrow definer entry points.

No conflicting existing objects were found, but the Study migration uses non-idempotent CREATE and drops a specifically named constraint. Debate uses IF NOT EXISTS / CREATE OR REPLACE. Therefore any newly appearing candidate object or partial migration must stop application for comparison; neither a Study retry nor Debate's IF NOT EXISTS is proof that a partially installed schema is compatible.

The Study ALTER TABLE will acquire a strong catalog lock and validate its widened constraint. Its five-second lock and thirty-second statement timeouts must be respected; do not terminate another session to force installation. Standard hosted PostgREST DDL/drop watchers are present. The metadata review does not prove the service-role Data API has refreshed its callable function inventory after future application.
