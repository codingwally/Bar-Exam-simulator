Forward migration `20260907143119_astra_late_149_binding_reconciliation.sql` requires both the reviewed historical-proof v4 migration and the STABLE 149 binding bridge. Their original SQL is unchanged. This migration can follow either installation order; it does not publish pricing, change customer rows, or write a migration ledger itself.

The bridge retained the original 149 revision/plan/channel IDs for the authorized term-only amendment. The old v4 window ended those IDs at the internal clone publication. The new window evaluates the existing full-equivalence helper at that publication instant and recognizes only the direct source's **first continuous public-binding interval**. It ends at the earliest next genuine publication, original checkout/display bound, opening of another visible checkout-enabled plan, or **September 14, 2026 00:00 Asia/Manila (September 13 16:00 UTC)**. Unrelated same-price revisions and differing QR/beneficiary/association/content cannot acquire this compatibility provenance.

For every other source plan, the opening is the later display/checkout start and the closing is the earlier display/checkout end. Only a nonempty overlap intersecting the interval after clone publication can end the binding. Disjoint, merely touching, already-ended, hidden, disabled, and post-ceiling intervals do not shorten it. The first opening is exclusive for payment-time review. This models the existing bridge's time-varying second-plan predicate without changing the applied bridge.

If that other plan later closes and the original public binding reappears, this v4 reconciliation deliberately does **not** merge the separated intervals. New v4 proofs remain `needs_information` without provisional/paid access, and verified payment times in the later interval are not automatically honored. Existing v3/public behavior is unchanged; supporting later reappearance requires a separately reviewed disjoint-interval design. Thus this change is not a claim of complete multiphase availability support.

Before that boundary, source-ID first submissions follow the ordinary pending/provisional contract. At or after it, v4 saves first proofs as `needs_information`, with neither provisional nor paid access. Approval still requires a privileged reviewer, explicit `honor_verified_offer`, and a separately verified real payment timestamp inside the captured historical interval. A page left open is not payment evidence. Approval starts the attributable 720-hour purchased segment; submission does not. v2/v3 cached-worker behavior, proof locks, replay keys, review guards, and causal invalidation are untouched.

V4 submission history retains source IDs and separately records the exact effective-term lineage in either installation order. The helper's original upper bound remains provenance; `sourceBindingInterval: first_continuous` and `sourceBindingValidUntil` separately identify the bounded interval, which also supplies the authoritative `offerValidUntil`. Original payment date/reference fields stay null for proof-only intake. No migration or RPC invents a paid timestamp.

Previously saved holds with a conflicting old captured window remain under review. This migration does not rewrite submission history, reclassify an accepted hold, or bypass the approval window-equality check. Any such real record would require a separate audited evidence correction; no live records were inspected or changed for this work.
