## Admission and accounting contract

One project-policy row lock precedes all capacity mutations. Configured scopes pin issuer, product, room, event, session and their caps. Logical sessions bind issuer, actor UUID, product, event and session. A coincident UUID in staging and production is not one account, and the one-device restriction applies per product/session rather than globally. Event/session counts are issuer/product qualified; the overall project count remains shared. Clients cannot choose caps through the RPC. Future configuration changes must hold the same project lock and increment its revision. There is deliberately no policy-enabling API.

Every `reserved`, `issued`, `connected`, `uncertain` or `revoking` epoch consumes one seat. Only `released` is excluded. Tokens, disconnect notices, elapsed TTL and missing client heartbeats never decrement occupancy. External occupancy is included in project and mapped room/session/event checks; inconsistent totals fail closed. Freshness timestamps and external counts are supplied by a future trusted inventory process, not discovered by this module.

Default capability ceiling is100, with10 proposed reconnect slots reserved from normal admissions. These are not measured or approved available seats. This successor supports **sequential fenced replacement only** and does not spend the10 reserved slots. The exact last predecessor must already be released through validated revocation/absence, and every other epoch in that logical session must also be released. Reserved, issued, connected, uncertain or revoking predecessors block reuse. A second parallel replacement is denied by the project lock and latest-epoch binding. Room/session/event caps still apply; no12-seat Study room override or overlap is added. Same-epoch renewal retains its seat and does not debit a second allocation.

The first epoch creates a logical allocation of10–21,600 seconds, further bounded by scope policy, with one immutable server-derived deadline. It debits that entire interval once. A sequential successor supplies the same duration, inherits the original deadline, and cannot extend it or change event/session. The predecessor must be fenced before the successor receives any authorization within that original interval. The project retains the complete original debit; gaps, closure, expiry and retries never refund it. **Every new physical epoch still debits bytes separately**, because no trusted byte metering exists. Closing is allowed only after all epochs are released and never reopens/refunds that allocation.

Admissions fail when inventory/allocation expires, totals exceed the allocation, or an unreleased epoch outlives its reserved duration. There is no automatic termination of an ongoing scored debate. These are conservative **admission allocations**, not measured invoices, enforced bandwidth limits, or a guaranteed ceiling on already connected overtime. Provider metering, exact legacy uncertainty inventory/drain, existing Study commitments and an approved shared capacity/minute budget remain prerequisites to any activation. A dashboard's historical seven-day peak is not current occupancy.

## Token and release contract

The foundation issues no JWT. `markIssued` records a mint intention with at most a 30-second initial-token deadline inside the allocated duration. Future token code must validate room authorization and reservation immediately before and after asynchronous signing and before returning a token; a concurrent release must prevent that token from being delivered. The generic `mc-<epoch UUID>` identity is not silently compatible with the current Study or Debate identity validators; integration must explicitly migrate those bindings.

`requestRelease` persists a revoking state, command ID and timestamp before provider removal. `confirmReleased` requires that exact binding, an acknowledged revocation cutoff later than the recorded mint/release second, and subsequent positive absence observed within 15 seconds. Proof must identify the same project, room and epoch identity. Policy disablement does not prevent release. Replayed commands return the current reservation, not a stale usable state.

Read/replay is **not a new signing authorization**: it intentionally returns current recorded state without rerunning the grant transaction. The future issuer must obtain a fresh successful `markIssued`, then recheck policy/product permission and release state after asynchronous signing before delivery. A replay or recorded `issued` status alone must never mint a token.

The service coordinator must produce this proof from validated LiveKit responses. SQL checks its structure, time ordering and binding; SQL cannot independently verify a caller's provider observation. Tests use explicitly inert provider observations and never imply live fencing. Official LiveKit documentation states that connected clients receive refreshed tokens and that initial expiry does not remove reconnect rights; Cloud removal supports explicit revocation cutoffs. Webhook delivery is not guaranteed, so future reconciliation needs read repair as well as signed webhook handling:

- https://docs.livekit.io/frontends/reference/tokens-grants/
- https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/
- https://docs.livekit.io/intro/basics/rooms-participants-tracks/webhooks-events/

Unknown mutating responses remain held in the adapter; it does not automatically retry. The database still counts the physical epoch and persists accepted command receipts. `read` remains available for explicit reconciliation. The future coordinator must persist its operation manifest across process restarts; recreating an adapter does not resolve a previously unknown provider outcome.
