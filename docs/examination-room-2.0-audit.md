# Examination Room 2.0 beta: repository audit

Audit date: 2026-08-09 (Asia/Manila)  
Target branch: `agent/examination-room-2-beta-20260809`  
Baseline: `origin/main` at `c8d382d`

## Executive conclusion

The repository already contains a separate institutional examination engine under the `exam_room_*` namespace. It is the correct foundation for 2.0. The implementation should preserve its service-role-only database boundary, roster-bound candidate authorization, immutable confirmed question versions, server deadlines, revisioned answers, manual grading, sealed result releases, isolated Google Sheets backup outbox, and email queue.

The largest gaps are not a missing exam engine. They are an absent Beadle role, an authenticated-only/publicly ambiguous entry, server-only autosave, incomplete recovery and final-submission evidence, overly aggressive integrity behavior, limited authoring rules, and insufficient operational/accessibility verification. The upgrade is therefore additive and targeted; no working examination, Mock Bar, Subject Matter, or Bar Feels data model is replaced.

Classification meanings: **KEEP** preserves a sound capability; **MODIFY** changes behavior in place; **CONSOLIDATE** joins overlapping paths; **EXTEND** adds to a sound base; **REPLACE** retires a defective implementation behind the same product capability; **NEW** adds a missing capability.

## Architectural decisions

1. **One exam engine:** extend `exam_room_*`; do not create a parallel “2.0” database.
2. **Server authorization:** the Worker remains the only browser-facing database caller. RLS/forced RLS and revoked browser grants stay in place; every new RPC performs actor and scope checks because the Worker uses a server credential.
3. **Public cards are not roles:** Professor, Beadle, and Student cards only explain and route. Account, activation/assignment, roster, exam state, and server decisions grant authority.
4. **Immutable publication:** confirmation becomes a review milestone; publishing freezes a hash-addressed snapshot of instructions, ordered questions/points, and rules. An attempt pins that version.
5. **Operational state is compositional:** leave, connectivity, recovery, integrity, and accommodations are related records/derived flags, not destructive mutations of the exam lifecycle.
6. **Local-first, server-evidenced:** IndexedDB protects work on the current device; the server owns accepted revisions, session epochs, timing, admission, and receipts. The UI states exactly which side has acknowledged data.
7. **No fake lockdown:** browser events are noisy signals. 2.0 records and summarizes them but does not auto-fail, auto-submit, or destroy an attempt.
8. **Manual institutional grading in beta:** the existing official grading workflow stays human-controlled. AI grading is deferred pending privacy/provider/evaluation gates.
9. **No new camera collection:** physical verification and exceptions are recorded; image capture remains off pending a PIA, lawful-basis/retention decisions, and a deletion/access design.

## Current release blockers and gates

- Corrected-question pre-start replacement, reopened submission generations, and optional access-code mode are implemented behind the dark 2.0 rollout. The candidate-scoped Admin break-glass contract and UI are wired, but its local action gate remains deliberately false until a real Supabase MFA challenge + verify ceremony is implemented. All remain institutional release gates until their authenticated, race, recovery, notification, backup, and rollback matrices pass in a production-shaped staging environment.
- Durable one-way navigation and owner retrieval of uploaded model-answer files are not complete; their UI paths remain disabled rather than simulated.
- MFA policy for verified examiners and the privileged Admin path’s production authentication configuration are not yet proven. The Worker contract requires a non-refresh-AMR-backed AAL2 challenge no older than 15 minutes and exposes only safe authorization booleans to the dashboard, but the dashboard currently has no challenge/verify UI and therefore cannot enable the restricted action.
- A real staging migration, RLS/advisor review, authenticated browser matrix, and Google Sheets/Resend end-to-end test require approved staging credentials.
- Backup restoration/PITR capability and a documented restore drill must be confirmed before institutional release.
- Break-glass production authorization/log review, tamper-evident audit retention, retention schedules, legal holds, DSR operations, PIC/PIP allocation, lawful-basis matrix, subprocessor/cross-border review, and NPC registration assessment require owner/DPO/counsel decisions.
- Camera collection and secondary-email live-session recovery remain disabled/deferred.
- PDF extraction must fail safely to manual construction unless the runtime proves bounded, reliable text extraction. OCR is not part of this beta.
- Supported browsers/devices may be advertised only after the documented test matrix passes. Phones are unsupported for serious beta examinations.
